# Сервер аккаунтов и прогресса

Подготовительный этап: Node.js 22+ / Express / PostgreSQL. Сервер пока **не подключён**
к действующей странице регистрации. `ACCOUNTS_ENABLED=false` по умолчанию.
Это позволяет отдельно проверить приложение и базу без приёма данных учеников.
Не требуется S3: пользователей и статистику хранит PostgreSQL.

## Что реализовано

- Email и псевдоним, вход по шестизначному коду без пароля. Код действует 10 минут,
  допускает 5 попыток и становится недействительным после использования.
- Независимые подтверждения соглашения и согласия: версия, SHA-256 документа,
  время отметки на сервере, время подтверждения email и способ получения.
- HttpOnly-сессии на 7 дней; в production — Secure, SameSite=Lax, host-only cookie.
  В базе находятся HMAC кодов и токенов, а не их исходные значения.
- Ограничения отправки: 6 писем на адрес и 30 на IP за час; проверка — 100 запросов
  на IP за час. Лимиты находятся в базе и общие для нескольких экземпляров API.
- События ответов и тренировок с защитой от повторного подсчёта, отдельный учёт
  самопроверки письменных заданий; черновики с проверкой версии.
- Однократный перенос локального прогресса в пустой аккаунт, выход и удаление
  аккаунта с каскадным удалением его статистики. Для удаления нужен вход за последние 15 минут.

## Локальная проверка

```sh
cd server
npm ci
npm test
```

Тесты используют PGlite — PostgreSQL в WebAssembly: настоящие SQL-запросы,
миграцию и транзакции, без замен таблиц на JavaScript-моки. Исходящие письма
перехватывает тестовая заглушка, используются только адреса `.invalid`.
Сетевой доступ к Timeweb PostgreSQL и настоящему SMTP проверяется отдельно при подключении.

Для запуска с реальной базой скопируйте `.env.example` в `.env`, заполните значения.
Node сам не читает `.env`, поэтому локально используйте:

```sh
node --env-file=.env scripts/migrate.js
node --env-file=.env src/index.js
```

Не добавляйте `.env`, пароли или сертификаты с приватными ключами в Git.
При локальном запуске установите `NODE_ENV=development`,
`PUBLIC_ORIGIN=http://localhost:3000`. На этом этапе доступен API, а не интерфейс тренажёра.

## Подключение в Timeweb App Platform

Этот раздел используется после создания ресурсов в панели Timeweb. Код не создаёт
платные приложения или базы и не меняет конфигурацию существующего сайта.

1. Создайте управляемый PostgreSQL и серверное приложение в одном российском
   регионе с общей приватной сетью. Сеть выбирайте при создании приложения.
   Скопируйте приватный адрес, порт, имя базы и пользователя из параметров подключения.
2. Подключите репозиторий `Alexandra-Sark/ege-formula-trainer`, ветку
   `codex/registration-server-20261002`. Путь до директории проекта — `server`.
   Выберите Express / Node.js 24 (минимум 22).
3. Установка зависимостей — `npm ci --omit=dev`, команда запуска — `npm start`.
   Процесс слушает `0.0.0.0` и `PORT` (по умолчанию 3000). Укажите этот же внутренний
   порт в настройках приложения; внешним HTTPS занимается платформа.
4. Добавьте переменные из таблицы ниже в окружение **серверного** приложения.
   Пока оставьте `ACCOUNTS_ENABLED=false`; SMTP и AUTH_SECRET не нужны для проверки базы.
5. Выполните `npm run migrate` в рабочей директории `server` в окружении с доступом
   к приватной базе. Если панель не предоставляет выполнение разовой команды,
   используйте терминал сервера в той же сети или временную команду запуска
   `npm run migrate && npm start`, затем верните `npm start`.
   Миграция идемпотентна и защищена блокировкой от одновременного запуска.
   Она не удаляет существующие таблицы. Не открывайте базу всему интернету ради этой команды.
6. Откройте `https://ДОМЕН-ПРИЛОЖЕНИЯ/health`: ожидается
   `{"status":"ok","accountsEnabled":false}`. Затем `/ready`: ожидается
   `{"status":"ready"}`. Второй адрес проверяет базу и установленную миграцию.
   Если первый отвечает, а второй возвращает 503, подключение или миграция ещё не готовы.

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `PUBLIC_ORIGIN` | HTTPS-origin без пути и завершающего `/`, например `https://trainer.example.ru` |
| `ACCOUNTS_ENABLED` | `false` на этапе подключения |
| `PORT` | Внутренний порт приложения, например `3000` |
| `PGHOST` | Приватный адрес PostgreSQL из панели |
| `PGPORT` | Порт из параметров базы, обычно `5432` |
| `PGDATABASE` | Имя базы |
| `PGUSER` | Пользователь базы |
| `PGPASSWORD` | Пароль пользователя, только в окружении |
| `PG_POOL_MAX` | `5` для небольшого приложения; учитывайте суммарные подключения всех экземпляров |
| `PG_SSL_MODE` | `disable` только для подключения через изолированную приватную сеть; для публичного TLS — `verify-full` |
| `PG_SSL_CA_FILE` | Путь к сертификату CA провайдера, если он нужен для проверки PostgreSQL TLS |
| `TRUST_PROXY_HOPS` | `0` сначала; настройте число доверенных прокси после проверки топологии |

Не используйте `rejectUnauthorized=false` и не добавляйте параметры `sslmode`
через URL подключения: здесь используются отдельные `PG*` параметры.
Не доверяйте произвольному `X-Forwarded-For`: неправильная настройка прокси позволяет
обойти ограничения по IP. При `TRUST_PROXY_HOPS=0` IP видимого прокси может быть общим
для учеников, поэтому число доверенных переходов нужно проверить до включения аккаунтов.

На первом подключении можно выполнить миграцию пользователем из панели.
Для рабочего сервиса желательно выделить пользователя с правами чтения/изменения
таблиц, а миграции запускать владельцем схемы. Доступные роли зависят от тарифа базы.
Проверку `/ready` также нужно разрешить читать `schema_migrations`.

## Перед включением регистрации

1. Утвердить новые условия хранения облачного прогресса: действующая редакция
   соглашения описывает только локальное хранение. Отдельно утвердить политику
   и текст согласия, сведения об операторе и порядок работы с несовершеннолетними.
2. Добавить утверждённые HTML-документы в `server/legal/`; указать их имена,
   версии и SHA-256 в `legal/manifest.json`. Заполнить `operator.name`,
   `operator.address`, `operator.contact`; только после проверки поставить
   `accountsReady:true`. Готовность в манифесте — явное решение владельца,
   а не юридическая проверка содержания кодом.
3. Подключить SMTP: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`,
   `MAIL_FROM`. Для 587 — `SMTP_SECURE=false` с обязательным STARTTLS;
   для 465 — `SMTP_SECURE=true`. Сертификаты сервера проверяются.
   Настроить разрешённый адрес отправителя у почтового провайдера.
4. Сгенерировать секрет **на своём компьютере**, сохранить только в окружении:

   ```sh
   node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
   ```

   Полученное значение — `AUTH_SECRET`; одинаковое для всех экземпляров сервера.
   Замена секрета аннулирует существующие сессии, коды и их HMAC.
5. Настроить резервные копии PostgreSQL и проверить восстановление. Архив файлов
   сайта не содержит пользовательскую базу. Откат кода не заменяет восстановление базы.
6. Подключить интерфейс к API **через один origin**, затем проверить тестовым аккаунтом
   отправку письма, обе отметки, подтверждение, импорт и удаление. Только после этого
   установить `ACCOUNTS_ENABLED=true` для рабочего приложения.

Сейчас в манифесте лишь существующее соглашение, `accountsReady:false`.
Попытка включить аккаунты без трёх документов и сведений оператора остановит запуск.
При изменении файла без обновления хеша сервер также не запустится.
Хеш документа можно получить командой `sha256sum legal/ИМЯ-ФАЙЛА.html`.

**Один origin:** интерфейс и `/api/*` должны обслуживаться по одному сочетанию
протокола, домена и порта. На следующем этапе нужно либо направлять `/api/*`
через доверенный прокси к API, либо отдавать выбранные публичные файлы тренажёра
из того же приложения. Текущий сервер статические файлы тренажёра не отдаёт.
Два разных технических домена Timeweb автоматически единым origin не становятся.
Сервис не включает CORS для обхода этой архитектуры. `PUBLIC_ORIGIN` должен совпадать
с фактическим origin интерфейса. Нельзя отдавать корень репозитория как публичную папку:
там могут находиться серверные файлы и конфигурация.

## Контракт API

Все изменяющие запросы требуют `Origin: PUBLIC_ORIGIN`, POST/PUT — также
`Content-Type: application/json`. После входа дополнительно требуется
`X-CSRF-Token` из `/api/session`; cookie отправляется с запросом. Формы будущего
интерфейса не должны отправлять email до двух явно поставленных галочек.

| Метод и путь | Назначение |
|---|---|
| `GET /api/legal` | Флаг доступности аккаунтов, версии/хеши/URL документов |
| `GET /legal/terms`, `/legal/privacy`, `/legal/consent` | Текст доступного документа |
| `POST /api/auth/start` | Запрос кода: `purpose`, `email`, `nickname` для регистрации, `legal` |
| `POST /api/auth/verify` | Подтверждение: `challengeId`, шестизначный `code` строкой |
| `GET /api/session` | Пользователь и CSRF-токен |
| `POST /api/auth/logout` | Удаление текущей сессии |
| `DELETE /api/account` | Удаление аккаунта; нужен свежий вход |
| `GET /api/progress` | Общая статистика, черновики и их версии |
| `POST /api/progress/events` | Пакет от 1 до 50 событий |
| `PUT /api/progress/draft` | Черновик и ожидаемая версия |
| `POST /api/progress/import` | Однократный перенос существующего локального прогресса |

Пример тела `/api/auth/start` (версии и хеши берутся из `/api/legal`):

```json
{
  "purpose": "register",
  "email": "student@example.invalid",
  "nickname": "Ученик",
  "legal": {
    "terms": {"accepted": true, "version": "VERSION", "sha256": "HASH"},
    "consent": {"accepted": true, "version": "VERSION", "sha256": "HASH"}
  }
}
```

Для `purpose:"login"` псевдоним не требуется, действующие подтверждения документов
нужны также. Зарегистрированный email при повторной регистрации не меняет псевдоним.
Неизвестный email при входе получает такой же запрос кода; проверка не создаёт аккаунт.
Ответ отправки не сообщает, есть ли email в базе. Код не возвращается через API.

События прогресса:

```json
{"events":[
  {"eventId":"UUID-V4", "kind":"answer", "uid":"UID-ИЗ-БАНКА", "correct":true, "selfReviewed":false},
  {"eventId":"ДРУГОЙ-UUID-V4", "kind":"session"}
]}
```

Создавайте `eventId` один раз на действие, сохраняйте его до успешной отправки
и используйте при повторе. Повтор того же события не увеличивает счётчик;
тот же ID с другим содержимым даёт 409 и отменяет весь пакет. Для заданий
`proof`/`solution` нужен `selfReviewed:true`. Проверка результата выполняется
тренажёром: эти данные — учебная статистика пользователя, а не защищённая
экзаменационная оценка. Вся статистика выбирается по сессии, `user_id` от браузера не принимается.

Черновик: `{"uid":"UID","content":"Текст","expectedRevision":0}`.
После сохранения возвращается новая `revision`. Передайте её при следующей записи;
при 409 получите свежий прогресс и предложите пользователю разрешить конфликт.
До 12000 символов. Текст черновика нужно показывать через `textContent`/value, не `innerHTML`.

Импорт: `{"importId":"UUID-V4","progress":{...}}`, где `progress` — прежний объект
`egeUnifiedTrainerProgress1` с `sessions`, `weak`, `proofDrafts`. Нужен явный выбор
ученика; не импортируйте автоматически при каждом входе. Повтор того же снимка с тем
же ID безопасен. Другой импорт либо перенос в уже использованный облачный аккаунт
даёт 409. Устаревшие UID игнорируются и учитываются в `ignored`. `mistakes`
восстанавливаются по соотношению ошибок и правильных ответов; настройки гостевого
интерфейса не переносятся. Клиент не должен удалять локальный прогресс до подтверждения
сервера или показывать его следующему ученику после выхода.

## Обслуживание

`npm run cleanup` удаляет истёкшие коды, сессии и часовые лимиты. Сервер выполняет
это каждый час; можно дополнительно запускать команду внешним расписанием.
Неподтверждённый email хранится до истечения кода и ближайшей очистки (обычно до 70 минут).
Для ограничения частоты IP/email находятся только в HMAC-ключах до ближайшей очистки
после часового окна, не в бессрочной истории. HMAC не означает юридическое обезличивание.
История согласий, прогресс и черновики хранятся до удаления аккаунта; политику хранения
и отзыв согласия нужно согласовать до рабочего запуска. Удаление через API не удаляет
данные из уже сделанных резервных копий: их срок хранения задаётся отдельно.

Ошибки возвращаются как `{error, requestId}`; приложение не пишет email, коды,
токены, черновики и пароли в свои сообщения журнала. Логи прокси, инфраструктуры и SMTP
нужно проверить отдельно. `/health` проверяет процесс, `/ready` — схему и базу.
В production ответы не кешируются, запрещено встраивание API и документов во frame.
Сервер завершает текущие запросы при SIGTERM/SIGINT и закрывает пул соединений.
